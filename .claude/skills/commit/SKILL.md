## 커밋 절차

### 1단계: 변경사항 분석
git status와 git diff를 통해 현재 저장소의 변경사항을 확인합니다.

- 추적되지 않은 파일 (Untracked)
- 스테이징된 변경 (Staged)
- 수정된 파일 (Modified)

### 2단계: 논리적 단위로 분류
변경사항을 다음 타입으로 분류합니다:

- **feat**: 새로운 기능 추가
- **fix**: 버그 수정
- **refactor**: 기능 변경 없이 코드 구조 개선
- **chore**: 빌드, 의존성, 문서 등 기능과 무관한 작업
- **docs**: 문서 작성/수정
- **style**: 포맷팅, 세미콜론 등 스타일 변경
- **test**: 테스트 코드 추가/수정

여러 변경사항이 섞여 있다면, 논리적으로 의미 있는 단위로 나눠 별도 커밋하는 것을 권장합니다.

### 3단계: 한국어 커밋 메시지 작성
다음 형식을 따릅니다:

```
<type>(<scope>): <subject>

<body>
```

**형식 규칙:**
- `<type>`: feat, fix, refactor, chore, docs, style, test
- `<scope>`: 선택사항, 변경된 부분의 이름 (예: auth, dashboard)
- `<subject>`: 현재형, 명령형으로 작성. 마침표 없음. 50자 이하 권장
- `<body>`: 선택사항이지만 권장. 변경의 "왜"를 설명. 줄바꿈 72자

**좋은 예시:**
```
feat(auth): JWT 기반 인증 구현

사용자 로그인 시 JWT 토큰을 발급하고 검증하는 기능을 추가했습니다.
토큰은 1시간 유효하며 refresh 메커니즘을 지원합니다.
```

```
fix(api): 동시 요청 처리 중 race condition 해결

데이터베이스 쿼리를 트랜잭션으로 감싸서 동시성 문제를 해결했습니다.
```

### 4단계: 사용자 승인 후 커밋
변경사항, 커밋 메시지, 커밋할 파일 목록을 사용자에게 보여주고 승인을 받은 후 커밋을 실행합니다.

## 실행 흐름

1. **git status 출력** — 추적되지 않은 파일, 스테이징된 변경, 수정된 파일 표시
2. **git diff 요약** — 각 파일의 변경사항 미리보기 표시
3. **커밋 분류 제안** — 논리적 단위로 나눌지, 한 번에 할지 제안
4. **메시지 작성** — 각 커밋마다 한국어 메시지 작성
5. **사용자 검토** — 변경사항 + 메시지 표시하고 확인 요청
6. **커밋 실행** — 사용자 승인 후 `git commit` 실행

## 주의사항

- **기밀 정보 확인**: `.env`, 개인키, 자격증명 파일이 커밋되려 하면 경고하고 제외
- **빈 커밋 방지**: 변경사항이 없으면 커밋하지 않음
- **pre-commit 훅**: git hooks가 실패하면 그 내용을 보여주고 함께 해결
- **메시지의 "왜"**: 기술적 세부사항보다는 변경의 이유를 중심으로 작성

## 옵션

사용자가 다음과 같이 요청할 수 있습니다:

- **"커밋해줘"** — 모든 변경사항을 한 번에 커밋 (기본)
- **"커밋: 분할"** — 논리적 단위로 나눠서 여러 번 커밋
- **"커밋: --amend"** — 마지막 커밋에 변경사항 추가 (단, push된 커밋은 주의)
